## Technical validation plan — specified, not executed on images

Use the unchanged `database/image_validation.py`, contract **local-static-png-v1**: static 8-bit RGB/RGBA, non-interlaced PNG, only IHDR/IDAT/IEND chunks. Actual source limits are 5 MiB encoded bytes; 4096 pixels per edge; 4,000,000 pixels; 20 MiB decoded bytes; 1,024 chunks. SQL MIME enumeration does not enable JPEG/WebP/AVIF support.

After an independently approved acquisition gate, verify exact source/capture/file association; compute actual SHA-256 and byte size; compare retained revision/hash evidence; then validate signature, bounded lengths, CRC, header features, dimensions, chunk sequence, compressed/decoded sizes and scanline filters. A mismatch or unsupported feature must produce a rejection/placeholder. Do not strip ancillary metadata, rename, convert, resize, install decoders or substitute another file to make a sample pass. Rights and technical rejection remain separate outcomes.

For any later registered asset, the existing wrapper authorizes the requested operation **before** the trusted bounded local reader, validates measured metadata against the registered object, and rechecks authorization/binding afterward. It performs no acquisition, storage or serving. A return value is not a reusable grant. Tests must include stale/revoked/expired rights, mismatched source/capture/asset grant, wrong hash, replaced bytes, unsupported PNG features, rights change during read and uniform unauthorized errors. These byte/SQL/RLS/restore tests are **SPECIFIED, NOT RUN** in this wave.

## Proposed storage architecture and tradeoffs

| Option | Benefits | Risks / boundaries | Recommendation status |
|---|---|---|---|
| Immutable original files outside Git; tenant/scope-local content-addressed objects; database metadata/reference | Portable originals, independent hash verification and backups, reuse of existing asset/provenance/rights concepts | Filesystem permissions, exact metadata binding, orphan detection, backup consistency and revocation need implementation/tests; hashes are not authorization | Recommended PROPOSED local-private pilot |
| Database binary objects | One transactional metadata/byte backup boundary | Database size/backup load and delivery privileges grow; not the current Python validator's object-store implementation | Alternative PROPOSED; no new table/service |
| Provider object storage or CDN | Possible later delivery/scale tools | New credentials, billing, public/private ACLs, cache/retention/region/vendor and deployment decisions | DEFERRED; no provider selected |

The existing schema already separates `image_assets`, source records/captures, asset permissions and scoped associations. A filesystem object is proposed as immutable original bytes referenced by an exact asset/hash, not an invented new SQL model. Never borrow a permission from an unrelated source or image. A source-wide grant must actually cover the selected asset/use. Binary objects, source evidence and license lineage remain outside public Git; no storage root or service is created now.

Tenant authorization applies to metadata **and** bytes. A public perfume identity cannot publish a user's private source, photo, collection/list/price overlay or license evidence. Do not expose global hash lookup/dedup existence to other users. Any future reader derives the principal from accepted authentication, resolves an authorized asset internally, avoids arbitrary paths/URLs and rechecks exact active use/scope/source/asset rights before each read/display/export. Deny unavailable and unauthorized objects uniformly; do not leak local paths, existence, hashes, private sources or signed URLs in errors, counts, logs or caches.

Preserve original source/capture/hash/license records. Derivatives, if separately approved later, receive their own hash, parent lineage, transformation and change notice; allowed uses cannot exceed any relevant ancestor's grant, audience, expiry or project restriction. A replacement is a new asset with its own provenance; it cannot revive a restricted parent. Quarantine an uncertain/replaced object and deny its next use. Revocation/expiry, membership withdrawal or a complaint invalidates future delivery/cache references; preserve only audit material whose retention is permitted. Restore must reapply current denials before opening access. Blank expiry is not an invented expiry, and a changed web page/project withdrawal is not automatic legal revocation of a compliant CC grant.
