# Cache, offline and privacy policy

**PROPOSED — DPT-PLAN-010, documentation only.** Source inspection baseline: `168715bc9bc5fff968524074257dc106a8a63638`. No application authentication, principal provisioning, API, UI, real ranking, cache, source intake or media delivery is implemented by this document. [[System_Architecture_Refinement]], [[C4_Context_and_Container_Design]], [[Architecture_Owner_Review_Packet]] and [[State_and_Error_Contracts]] govern the connected proposal. Machine-readable acceptance design: [[Architecture_Security_and_Cache_Model.json]].

## Reconciliation and initial recommendation

Historical [[Site_Map_and_Screens]] proposes an offline-first PWA local cache. The newer [[Post_PR27_Application_Integration_and_Security]] recommends local-private ephemeral processing without shared caches, query history or durable results. These describe different stages, not an implemented offline capability. This amendment **PROPOSES** an initial online-only operational policy and retains offline/PWA capability as a conditional later roadmap feature requiring an exact rights, privacy, retention, revocation and implementation contract. It does not remove Cart, manual purchase status, Collection or Dashboard from the product roadmap.

Initially no service worker, IndexedDB, localStorage, persisted query client, shared server private cache, CDN media cache or offline write queue is permitted. No application cache exists by this design document. Content-hashed generic UI files alone may be candidates for ordinary HTTP caching after explicit build review; they must contain no user data, catalogue rows, source-derived images, session material or embedded private initial state. Source data does not become a UI asset by bundling it.

Every operational row below uses fresh authorization/rights evaluation and request-local data plus the current authorized render only. Proposed HTTP behavior is `Cache-Control: no-store` for operational requests/responses, including denial/error responses and media. Framework server rendering, fetch/data caches, client query libraries, prerendering, link prefetch and browser back/forward restoration must be reviewed explicitly; defaults are not evidence of isolation. No framework/configuration is selected here. Existing private buying-source/purchase data coverage includes separately authorized manual purchase-history records; the purchase-record interface adds no cache class, persistence permission or retention default.

## Rights and revocation through each operation

Storage, cache, private display, public display, transform, redistribution, research and AI use are distinct actions. The existing SQL rights model includes operation-specific grants; absence or unknown evidence is denial. An allowed display request cannot create a persistent result, image thumbnail, export or cache without its own allowed action and approved project policy. Public entity scope is not a grant for private linked observations, images, listings or overlays.

Before lookup, counts, pagination, candidate expansion, scoring, source-link projection or asset reads, check the current principal and operation. Recheck after long work and immediately before publication/delivery. On membership or rights withdrawal, expiration, logout or scope change, deny subsequent operations; stop pending projection/delivery, clear controlled request/render buffers, invalidate unpublished responses and discard compromised leases. In-flight cancellation is best effort. A later exact implementation contract must specify the race window and failure behavior without promising instantaneous retroactive revocation.

RFC 9111 `private` permits private-cache storage, so it is not equivalent to the proposed no-store policy. RFC no-store constrains compliant caches but does not guarantee privacy or remote erasure. Browser memory, history restoration, extensions, screenshots, user downloads, network intermediaries or malicious caches cannot be reliably erased by a server directive. Clear owned temporary object URLs/buffers and managed renders where possible; never state that logout deletes all delivered data. These limits come from S-SEC-11 in [[Architecture_Technical_Research_Security]], not a verified browser implementation.

## Offline UI and recovery

A generic cached shell may say **Offline** without embedding stale private results. Catalogue, matching, comparison, buying sources, collection, dashboard and media operations are **Unavailable** until a fresh authorized request succeeds. No synthetic zero score, stale result fallback, old private thumbnail, cached permission, automatic queued write or order placement is allowed. Unsaved user intent may exist only in current controlled memory under the current session; persistence needs a future approved policy. Show a safe retry action; authenticate/rebind/recheck after reconnection before retry. Never automatically resubmit a mutation with uncertain completion.

## Conditions for a later offline/PWA amendment

Any future amendment must name the exact data classes/actions and evidence for cache/retain/share rights, audience, encrypted storage and key/session lifecycle, quotas, versioned principal/scope keys, expiration, withdrawal, backups, browser recovery, device sharing, offline authorization limits and no-echo errors. It must assess what cannot be revoked offline and obtain explicit Owner acceptance. Public catalogue caching also needs exact field/source publication and cache rights; it is not automatically safe. Static-shell caching cannot silently expand into an offline application database.

The old packet `POST27-ODP-1` remains immutable. This policy refines its G/H architecture and private-cache implications for a newly versioned [[Architecture_Owner_Review_Packet]]; it is not acceptance of G/H or A/B/I. No accepted numeric cache lifetime, session timeout, retention period, browser storage provider or CDN policy is invented. The three/one-second limits in the existing adapter remain statement/lock bounds, not cache TTLs.

## Acceptance and limitations

SEC-N05/06/08/10/11/12/14 in [[Authorization_and_Trust_Boundaries]] cover stale grants, user switching, pool cleanup, errors, cache inspection, restore and offline/logout. They are **NOT RUN**. A future approved implementation must inspect actual framework and browser storage behavior, response headers, canceled requests and history restoration with different genuine principals. Static architecture checks establish matrix coverage and consistency only; they cannot prove cache behavior. No service worker, storage, header, database, role, browser or Production setting changed.
