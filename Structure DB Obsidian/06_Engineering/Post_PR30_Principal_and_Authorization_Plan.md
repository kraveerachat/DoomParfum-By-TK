## Initial proof and server session — proposed profile, not selected provider

Recommend evaluating **OIDC authorization-code flow with PKCE S256** as one concrete proof profile, with an established maintained auth/session implementation. Alternative: a separately specified local passkey/WebAuthn proof contract. Provider, framework, library/version, supported signing algorithm and exact discovery/JWKS lifecycle remain **UNSELECTED**; none can be silently defaulted. APP-02/04 design acceptance cannot start runtime until an exact Owner-selected proof/provider/dependency/secret-custody contract exists. No OIDC/WebAuthn conformance claim is made by this proposal.

Primary protocol references retrieved2026-11-17: [OpenID Connect Core1.0 incorporating errata2](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation), dated2023-12-15, and [RFC7636](https://www.rfc-editor.org/rfc/rfc7636), September2015. Candidate checklist and local session budgets are this project's proposal, not numbers mandated by those references. WebAuthn is an unassessed alternative here; exact current standard/library support is UNKNOWN and requires its own approved contract evaluation.

For the OIDC candidate, the later exact contract must pin issuer, client/audience, one allowed callback, approved signing algorithm/key policy, TLS trust, server-held credentials where needed, PKCE, state, nonce, token type, signature/issuer/audience/authorized-party checks, exp/nbf/iat/auth_time policy, replay and revocation. Browser-provided decoded token fields are never verified claims. Accept an identity only after server validation; do not auto-enrol unapproved subjects, link accounts by email or allow browser-chosen scope. Redirect return targets are same-origin allowlisted route identities without arbitrary external URLs. No private source/query/object information goes to an external identity provider.

| Proposed session policy | Exact value / meaning |
|---|---|
| Session secret | 32 cryptographically random bytes; base64url without padding, 43 characters; opaque, no embedded subject/scope/DB credential; server stores a verifier, not plaintext token. |
| Browser custody | `__Host-` cookie name under exact future contract; Secure, HttpOnly, Path=/, no Domain, SameSite=Strict; TLS mandatory. No token in URL, localStorage, IndexedDB, analytics or UI DTO. Cookie/proof <=4096bytes per POST30-READ-BUDGET-1. |
| Session life | 15-minute idle expiry, 8-hour absolute expiry, no silent extension beyond absolute expiry; clock tolerance <=30s for accepted initial provider proof only. Internal logout/revocation and source-rights deadlines have no 30s grace. |
| Proof freshness | Initial proof authentication age <=5minutes; unused login flow/state/nonce lifetime <=5minutes and single-use. Exact algorithm/provider token schema remains blocked until selected; reject an incompatible provider rather than widening limits silently. |
| Renewal / binding | Rotate on successful authentication and explicit reauthentication; session record binds exact immutable issuer+subject, internal app actor, approved LOGIN, allowed scope references, session generation, policy version, created/last-seen/expiry/revoked state. Privilege changes require fresh binding and generation; no session fixation reuse. |
| Request verification | Verify cookie/session verifier, audience, active generation, expiry, issuer-subject binding and revocation on every service operation and final publication. No durable “authenticated=true” cache. Login/session-end require exact same-origin/CSRF contract; cookie presence is not proof. |
| Session admission | At most3 active sessions per subject; a fourth requires explicit authenticated session management or denial, not unbounded issuance. At most5 failed initial-auth attempts per subject-independent admission key per60seconds; exact privacy-preserving network/issuer rate-limit key requires acceptance and never logs raw credential. |

These session values are **PROPOSED**, part of APP-04/06 review. They are not deployment defaults. If the selected provider cannot meet them, revise/version/accept the exact contract. Subject-independent failure handling must avoid revealing whether an account exists. Session create/end is security lifecycle, not authorization for perfume/personal-record writes.

## Least-privilege grant and RLS prerequisite

Recommend a **new separately approved catalogue reader role/repository boundary**, with a proposed role identity `dpt_catalogue_reader` (not created), without inheriting the existing broad dpt_runtime/dpt_writer/dpt_curator/dpt_owner roles. Genuine per-subject LOGINs have only the accepted reader capability. No superuser, BYPASSRLS, CREATEROLE, CREATEDB, REPLICATION, ownership, broad CREATE/TEMP privileges, SET-to-privileged-role path or arbitrary function execution. Inspect direct, PUBLIC and indirect memberships/grants, INHERIT/SET options and dangerous security-definer reachability. A NOINHERIT label alone proves nothing.

This needs a **later new migration and adapter contract**, never edits to migrations001–008. Existing `read_profile`'s dpt_runtime admission and table grants mean it cannot simply be used unchanged for this new role. Do not claim the proposed reader already works or weaken its guard by string replacement. A safe future contract may use explicitly authorized catalogue projection views/functions with locked search_path, no arbitrary SQL/field/scope parameters, minimal EXECUTE/USAGE, and exact per-subject RLS semantics. A security-definer implementation must prove how it preserves original session_user scope, object/field/use checks and does not use owner bypass to fetch everything. A security-invoker design must prove underlying privileges and raw-evidence nonexposure. Choice and exact ACL list are **UNSELECTED/BLOCKED** until independently reviewed; this plan grants no function privileges.

The later grant manifest must enumerate every accessible table/view/column/function/schema, owner, default privilege, PUBLIC grant, recursive membership/SET path and RLS policy, including intentional helper paths. Deny direct read of unselected/raw evidence, private review dossiers, other users' personal tables and unrelated mutation/operator functions. Schema usage alone is not data permission. All row and field gates remain active for authorized repository execution; application filtering supplements, never substitutes for, DB enforcement. Current can_read_scope admits public rows; first-slice application policy must additionally constrain the exact approved application scope instead of taking all public or shared rows by default.

If minimum-grant proof cannot preserve current schema semantics, defer reads or amend the future contract through review. Never solve this by publishing source rows, removing FORCE RLS, granting curator/owner membership or using a privileged fallback.

## Request, connection and publication sequence

1. **Admission:** enforce untrusted-byte/depth/rate/concurrency bounds and strict schema without target lookup. Authenticate initial/current proof and verify server session. Select operation from an allowlist. `IF-AUTH-SESSION-1` is a logical contract, not an implemented issuer.
2. **Binding:** trusted server resolves immutable issuer+subject to app actor/LOGIN and approved scopes. Reject supplied actor/role/scope overrides and missing/changed binding. Never derive a DB role from profile UUID, query text or browser identity. `IF-PRINCIPAL-LEASE-1` stays internal.
3. **Initial connection:** open a physical connection authenticated originally as the exact nonadmin LOGIN, using server-only credential custody under separately approved authentication configuration. Verify authenticated-origin evidence from the selected driver/server trust path, session_user/current_user equality at admission, expected database/server and immutable mapping. An existing admin pool cannot produce this proof. Inspect effective privileges against accepted manifest, not just role labels.
4. **Transaction:** start a fresh READ COMMITTED READ ONLY transaction with row_security on, bounded statement/lock/idle limits and accepted search_path. Current adapter uses 3s/1s per statement; proposed total server deadline is5000ms including acquisition/projection/final gate, never a reset for each sub-operation. Browser cannot submit SQL or transaction settings.
5. **Authorization before data exposure:** derive exact current scope permission, object/action/use policy and authorized selected-field relation inside the repository query. Apply rights/selection/conflict/materialization checks to the queryable relation **before** text filtering, sort, page expansion, has_more or any count. Do not privileged-fetch hidden rows then filter in Python. A returned public perfume does not publish related private brand/source/observation/media/personal rows. No inaccessible object-specific metadata or denied-field label leaks.
6. **Projection:** source claims become user-facing facts only through reviewed selected fields under exact accepted mappings. Current storage/display/automation evidence, dates and source rights must pass; cache/redistribution/media require separate permissions. Check selected source version/observation, field/entity identity, materialized value, no open or incompatible resolved conflict, scope and membership. Missing selected field becomes unknown/unavailable only when that field's existence/status itself is authorized. Partial note members remain incomplete, never full-domain absence. Matching remains disabled; no scorer invocation.
7. **Final gate:** serialize to a bounded private request buffer, then recheck fresh session generation, scope/membership, selection/conflict snapshot and rights against current time, not original transaction/statement timestamp. Reauthorize all emitted fields; a changed epoch or review deadline discards the prepared projection. Gate must be within100ms before enqueue or repeated. Read-committed statements alone cannot guarantee instantaneous revocation. Exact epoch authority/atomic publication coordination is not implemented and must be accepted/tested in the service contract.
8. **Completion:** only after successful final gate enqueue one non-streaming response. Roll back/read-transaction close on success, error, cancellation, disconnect, logout or timeout as appropriate; no writes to source/personal records. Release nothing to a shared cache. Audit only safe bounded metadata under separately accepted access/retention. Publish UI only if session/view/request generation is still current.

The final gate's100ms and total deadline are proposed controlled server bounds, not guarantees about browser receipt. Rights change after approved enqueue cannot retract bytes already sent; cancellation/clearing is best effort. If a requirement demands stronger atomicity, the exact implementation must coordinate revocation/publication rather than claiming RLS snapshots solve it.

## Pool, cancellation and logout

Start with dedicated per-request physical connections for the small pilot, or an explicitly approved pool partitioned by **genuine initial LOGIN plus database, credential generation and session policy**. Dedicated connections avoid cross-subject reuse but do not replace origin, ACL or cleanup proof. A pool authenticated asA is never repurposed asB with SET ROLE/GUC/context reset. Do not share in-flight connection, transaction, cursor, result buffer, prepared state or domain cache across subjects.

Acquisition500ms and total5000ms are hard limits; at most2reads/session and8globally. Timeout/disconnect/cancel/logout invalidates request generation, signals query cancellation, rolls back and waits up to1000ms for acknowledgement/cleanup. Do not swallow cancellation and publish a late result. If acknowledgement, transaction state, reset or identity is uncertain, close/discard the physical connection and buffered projection; no retry under admin or another identity. A later reusable pool requires clean idle transaction state, validated original identity/privileges, no orphan work and per-borrower isolation tests. “RESET ALL” alone does not prove origin or remove all state.

Logout invalidates the server session/current generation before acknowledging, cancels active requests, closes/discards its leases, clears controlled UI/private memory and cookie, and returns the same safe ended result for repeated/unknown session requests. It does not revoke other sessions without separate accepted authority. Revoked/expired session, shared membership, selected observation or source right invalidates unpublished data and cursors immediately at the trusted authority, with final rechecks as above. Rotation/revocation of DB credentials and server sessions must be coordinated; no pooled credential survives its generation. No offline retry/replay of private reads after logout.

## Error, cache and audit privacy

Use POST30-READ-1 safe errors and POST30-READ-BUDGET-1 in the companion ADR. A valid session gets one unavailable shape/status for inaccessible/malformed/nonexistent/hidden/revoked/expired profile references. No target-specific invalid-ID diagnostics, count, selected raw path, source key, SQLSTATE, constraint name, storage key or credential may reach browser/log. A wholly unauthenticated request may be told authentication is required independent of target. Capacity and structural errors have fixed classes; compare timing experimentally, do not assert constant-time behavior.

Denied-field details are server-only; authorized unknown/incomplete facts are distinct from canonical values and never produce zero. Fit, Data Confidence, Direct Pairwise Evidence, matching eligibility and source rights are separate channels. First slice has no scoring/confidence metric/pairwise evidence fetch; a disabled notice is static capability scope, not a per-object rights oracle. Minimal provenance contains only allowed attribution/review metadata; mandatory notice denied/oversized means field unavailable.

Operational data and errors are no-store/private and request/render-local. Disable private prefetch, shared/framework/CDN persistence, localStorage/IndexedDB, service-worker API caching and raw query/session telemetry. Shell assets contain no personal data. Proposed initial audit fields: opaque request correlation, server-only pseudonymous actor reference, operation class, gate result, policy version and bounded timestamp; no raw values, token, DB credential, private query or concealed object ID. Audit implementation/storage/access/retention are **UNSELECTED** and a blocking exact-contract requirement, not an invented durable data-retention permission. Security revocation state required for enforcement is separate from optional analytics.
